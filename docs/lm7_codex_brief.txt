LM7 — CODEX DEVELOPMENT BRIEF
=============================

Repository
----------

GitHub: https://github.com/lmontigny/lm7

Assume that the repository may initially be empty or contain only minimal
scaffolding. Inspect and preserve existing files before making changes.


1. PRODUCT VISION
-----------------

LM7 should let a PyTorch user run the same inference model on different
hardware by changing one line:

    import lm7

    model = lm7.compile(model, target="auto")
    output = model(inputs)

Explicit hardware selection should also be possible:

    model = lm7.compile(model, target="nvidia:h100")
    model = lm7.compile(model, target="amd:mi300x")
    model = lm7.compile(model, target="intel:gpu")
    model = lm7.compile(model, target="cpu")

The user selects hardware, not a compiler. LM7 selects and invokes the best
existing compiler/runtime for that target.

LM7 is NOT intended to be another ML compiler built from scratch. It is a
PyTorch-first frontend, compiler orchestration layer, artifact cache, and
unified runtime interface.


2. CORE PRODUCT PROMISE
-----------------------

Primary statement:

    Run the same PyTorch inference model on any supported accelerator by
    changing one line.

Desired user experience:

    model = lm7.compile(model)

This should:

1. Detect available local hardware.
2. Determine which installed compiler backends support that hardware.
3. Select a backend using a documented policy.
4. Lazily capture the model on the first invocation.
5. Compile or retrieve a cached artifact.
6. Move inputs and weights when automatic transfers are enabled.
7. Execute the model.
8. Return PyTorch-compatible outputs.

The first version should prioritize correctness, clear behavior, and a clean
extensible architecture over maximum model coverage or peak performance.


3. IMPORTANT DESIGN PRINCIPLES
------------------------------

1. Do not write a new graph compiler.
2. Do not introduce custom MLIR dialects or optimization passes in v1.
3. Use torch.export.ExportedProgram as the common source-level graph contract
   when an export is required.
4. Do not prematurely lower every backend through StableHLO or another common
   low-level IR. Native backends should receive the richest representation they
   support.
5. Keep hardware targets separate from compiler backends:

       target="nvidia:h100"
       backend="auto"

   not:

       target="triton"

6. Backends must be plugins behind stable LM7 interfaces.
7. Make heavy dependencies optional. Importing lm7 should not require IREE,
   TensorRT, OpenVINO, XLA, Neuron, or even a GPU-enabled PyTorch wheel.
8. Provide deterministic and inspectable selection. Users must be able to ask
   why a target/backend was selected.
9. Prefer an eager fallback during early development, with an explicit warning.
10. Offer a strict mode for production that forbids silent fallback.

5. PUBLIC API
-------------

Minimum API:

    lm7.compile(
        model,
        target="auto",
        *,
        backend="auto",
        mode="lazy",
        transfers="automatic",
        fallback="warn",
        cache=True,
        options=None,
    )

Proposed semantics:

target:
    "auto"                  Best supported local target
    "cpu"                   Local CPU
    "nvidia"                Any local NVIDIA GPU
    "nvidia:h100"           NVIDIA H100 class
    "nvidia:sm90"           NVIDIA compute capability
    "amd"                   Any local AMD GPU
    "amd:mi300x"            AMD MI300X
    "amd:gfx942"            AMD architecture
    "intel:gpu"             Intel GPU
    "apple:metal"           Apple GPU
    "tpu"                   Google TPU, later
    "aws:trainium"          AWS Trainium, later

backend:
    "auto"                  Planner selects backend
    "eager"                 PyTorch eager fallback/reference
    "inductor"              TorchInductor
    "aot_inductor"          AOTInductor
    "iree"                  IREE/Turbine
    "openvino"              OpenVINO
    "tensorrt"              Torch-TensorRT/TensorRT
    "xla"                   PyTorch/XLA
    "neuron"                torch-neuronx

mode:
    "lazy"                  Compile on first invocation
    "aot"                   Require example inputs or an ExportedProgram
    "eager"                 Do not compile

transfers:
    "automatic"             Wrapper moves inputs/weights as needed
    "explicit"              Inputs must already be on the target device

fallback:
    "warn"                  Fall back and emit a clear warning
    "error"                 Fail if selected compilation is unavailable
    "silent"                Allowed only if deliberately implemented/documented

Useful secondary APIs:

    lm7.detect_targets()
    lm7.explain(model=None, target="auto")
    lm7.backends()
    lm7.clear_cache()
    lm7.version()

Potential CLI:

    lm7 doctor
    lm7 targets
    lm7 backends
    lm7 cache list
    lm7 cache clear

Environment variables:

    LM7_TARGET=amd:mi300x
    LM7_BACKEND=auto
    LM7_CACHE_DIR=/path/to/cache
    LM7_FALLBACK=warn
    LM7_LOG_LEVEL=INFO

Explicit function arguments must override environment variables.


6. TARGET AND BACKEND ARE DIFFERENT CONCEPTS
--------------------------------------------

Target identifies where execution happens:

    TargetSpec(
        vendor="nvidia",
        kind="gpu",
        architecture="sm90",
        model="h100",
        ordinal=0,
    )

Backend identifies which software stack compiles and executes:

    BackendInfo(
        name="aot_inductor",
        version="...",
        supported_targets=[...],
        priority=...,
    )

The user normally provides only a target. The planner resolves a backend.


7. INITIAL BACKEND POLICY
-------------------------

Long-term candidate matrix:

NVIDIA GPU:
    Primary candidates:
        - Torch-TensorRT with AOTInductor fallback
        - AOTInductor/TorchInductor
    Kernel paths selected internally by those projects may include:
        - Triton
        - CUTLASS
        - CuTeDSL
        - cuBLAS/cuDNN
    Additional candidate:
        - IREE CUDA

AMD GPU:
    Primary candidate:
        - TorchInductor/AOTInductor with Triton and ROCm libraries
    Additional candidates:
        - IREE ROCm
        - MIGraphX where useful

Intel GPU:
    Primary candidates:
        - OpenVINO
        - TorchInductor XPU
    Additional candidate:
        - IREE Vulkan

x86 CPU:
    Primary candidates:
        - AOTInductor CPU
        - OpenVINO/oneDNN
    Additional candidate:
        - IREE LLVM CPU

Apple/mobile:
    Later:
        - Core ML or ExecuTorch delegates
        - IREE Metal/Vulkan

Google TPU:
    Later:
        - PyTorch/XLA -> XLA -> PJRT

AWS Trainium/Inferentia:
    Later:
        - torch-neuronx -> Neuron compiler/runtime

New accelerators:
    Later:
        - StableHLO/PJRT vendor plugin
        - IREE HAL/target plugin

Do not implement all these adapters in the first milestone. The architecture
must make them possible without changing the public API.

    import lm7

10. CORE TYPES
--------------

Target specification:

    @dataclass(frozen=True)
    class TargetSpec:
        vendor: str
        kind: str
        architecture: str | None = None
        model: str | None = None
        ordinal: int | None = None
        remote: bool = False

Detected hardware:

    @dataclass(frozen=True)
    class DeviceInfo:
        target: TargetSpec
        name: str
        total_memory_bytes: int | None
        capabilities: Mapping[str, Any]

Compilation request:

    @dataclass(frozen=True)
    class CompileRequest:
        model: torch.nn.Module
        target: TargetSpec
        mode: str
        transfers: str
        fallback: str
        options: Mapping[str, Any]

Backend support result:

    @dataclass(frozen=True)
    class Support:
        supported: bool
        reason: str
        priority: int = 0

Compiled result:

    @dataclass
    class Artifact:
        backend: str
        target: TargetSpec
        callable: Callable | None
        path: Path | None
        metadata: Mapping[str, Any]

These exact names may change if a cleaner implementation emerges, but preserve
the conceptual separation.


11. BACKEND CONTRACT
--------------------

The first contract should be intentionally small:

    class Backend(Protocol):
        name: str

        def probe(self) -> BackendInfo:
            ...

        def supports(self, request: CompileRequest) -> Support:
            ...

        def compile(
            self,
            request: CompileRequest,
            example_args: tuple[Any, ...],
            example_kwargs: Mapping[str, Any],
        ) -> Artifact:
            ...

        def load(self, artifact: Artifact) -> Callable:
            ...

The registry:

    registry.register(EagerBackend())
    registry.register(InductorBackend())

Third-party packages should eventually be able to register through Python entry
points, for example:

    [project.entry-points."lm7.backends"]
    my_backend = "my_package.backend:create_backend"

Do not require entry-point support in the first commit unless it remains simple.


12. LAZY MODULE BEHAVIOR
------------------------

lm7.compile() should immediately return a wrapper around the original model.

Before first invocation:

    wrapper.state == "uncompiled"

On first invocation:

1. Derive an input signature.
2. Resolve the target if it was deferred.
3. Ask the planner for a backend.
4. Compile.
5. Cache the resulting callable/artifact.
6. Execute.

Later calls:

1. Derive input signature.
2. Reuse a compatible compiled variant.
3. If incompatible, compile a new variant or fail according to configuration.

Thread safety:

- Compilation for the same signature must happen once.
- Other callers should wait for the result.
- Failed compilation should not leave the wrapper permanently corrupt.
- Keep the first implementation simple; a lock per wrapper is acceptable.

Preserve important nn.Module behavior:

- eval()/train() should delegate or be explicitly constrained to inference.
- state_dict() should remain accessible.
- parameters() should remain accessible.
- attributes not owned by the wrapper should delegate to the wrapped module
  where safe.

The project is inference-first. If model.training is True, warn or reject in
strict mode.


13. DEVICE DETECTION
--------------------

Detection must be best-effort and never crash merely because an optional
backend is not installed.

Possible checks:

1. CPU is always present.
2. NVIDIA:
       torch.cuda.is_available()
       torch.cuda.get_device_properties()
3. AMD:
       torch.cuda.is_available() may also be true on ROCm builds.
       Inspect torch.version.hip and device properties.
4. Intel XPU:
       Check torch.xpu only if the attribute exists.
5. Apple MPS:
       Check torch.backends.mps only if present.
6. TPU/XLA:
       Probe only when the optional integration is installed.

Never import heavyweight optional packages at module import time.

Auto-selection v1:

1. Explicit target, if provided.
2. Environment target, if provided.
3. Supported local GPU with the highest planner priority.
4. CPU.

Do not claim cost-based or global cloud selection in v1.

Return rich diagnostics:

    lm7.detect_targets()

could produce:

    [
        DeviceInfo(target=TargetSpec("nvidia", "gpu", "sm90"), ...),
        DeviceInfo(target=TargetSpec("cpu", "cpu", "x86_64"), ...),
    ]


14. BACKEND PLANNER
-------------------

Planner inputs:

- Target
- Installed backend capabilities
- User backend override
- Requested mode
- Model/export compatibility when known
- Precision/quantization options later

Planner output:

- Selected backend
- Ranked alternatives
- Human-readable reasons

Example explanation:

    Selected aot_inductor for nvidia:sm90

    Reasons:
    - Target is an NVIDIA CUDA GPU.
    - AOTInductor is installed and supports this mode.
    - TensorRT adapter is not installed.

    Alternatives:
    - eager: supported, lower priority
    - iree: unavailable because iree-turbine is not installed

Selection must be deterministic.


15. EAGER BACKEND
-----------------

The eager backend is required as:

- A correctness reference
- A fallback
- A way to test the full architecture without optional compilers

It should:

- Report support for local PyTorch devices.
- Move the model to the selected device when transfers are automatic.
- Move tensor inputs recursively.
- Run under torch.inference_mode() unless deliberately configured otherwise.
- Return normal torch.Tensor/nested outputs.
- Emit a warning when chosen as fallback after compilation failed.

Avoid silently catching arbitrary model execution errors. Only compilation or
backend-availability failures should trigger configured fallback.


16. INDUCTOR BACKEND
--------------------

Initial behavior may use:

    torch.compile(model, backend="inductor")

The adapter must:

- Check that torch.compile exists.
- Avoid compiling during backend probing.
- Preserve options such as dynamic and mode if provided.
- Return useful exceptions with backend context.
- Avoid depending directly on unstable torch._inductor APIs in the first
  milestone unless required.

Later, add an AOTInductor adapter based on torch.export and
aoti_compile_and_package. Keep JIT Inductor and AOTInductor as distinct backend
names because their artifact/runtime behavior differs.


17. INPUT AND OUTPUT TRANSFERS
------------------------------

For the one-line experience:

    transfers="automatic"

The wrapper should recursively map tensors through:

- positional arguments
- keyword arguments
- tuple/list
- dict
- simple dataclass/namedtuple structures if easy

Avoid modifying user-owned input structures in place.

Explicit transfer mode:

    transfers="explicit"

must validate that tensor inputs are already on the expected device and produce
a clear error otherwise.

Returning outputs:

- In the initial local PyTorch implementation, return tensors on the selected
  device.
- Do not automatically move potentially large outputs back to CPU.
- Later runtimes may use DLPack for zero-copy interchange.


18. CACHE DESIGN
----------------

The first milestone can cache compiled callables in memory.

Add filesystem cache scaffolding without pretending arbitrary compiler objects
are serializable.

Cache key inputs should eventually include:

- Model structure hash
- Weights hash or stable identity
- Input shapes, dtypes, strides, and relevant values
- Dynamic-shape profile
- Target specification
- Backend name and version
- PyTorch version
- Compiler configuration
- Precision/quantization configuration
- LM7 version

Do not hash all large weights on every invocation. The first implementation may
use an in-process model identity and clearly document that persistent artifact
hashing is future work.

Default cache location:

    ~/.cache/lm7

Allow override with LM7_CACHE_DIR.


19. ERROR MODEL
---------------

Define specific exceptions:

    LM7Error
    TargetNotFoundError
    BackendUnavailableError
    UnsupportedModelError
    CompilationError
    ArtifactLoadError
    InputDeviceError

Messages should always include:

- Requested target
- Selected backend, if any
- Failing stage
- Original exception summary
- Suggested next action

Do not leak giant compiler traces by default. Preserve them under debug logging
or as chained exceptions.

30. TECHNICAL CONTEXT AND RATIONALE
-----------------------------------

ZML uses approximately:

    Zig model definitions
        -> symbolic ZML tensors
        -> MLIR/MHLO
        -> OpenXLA
        -> PJRT
        -> hardware

LM7 deliberately differs:

    PyTorch ExportedProgram
        -> target planner
        -> best existing compiler for each target
        -> unified LM7 module/artifact interface

For NVIDIA, a native path may use AOTInductor or Torch-TensorRT. Inductor may
select Triton, CUTLASS, CuTeDSL, cuBLAS, or other implementations internally.

For AMD, Inductor/Triton and IREE ROCm should eventually be compared rather than
assuming one is universally better.

For Intel, OpenVINO and Inductor XPU are natural candidates.

IREE remains valuable for portable AOT compilation, compact runtimes, Vulkan,
Metal, CPU, CUDA, and ROCm, but LM7 should not force all targets through IREE.

Triton is a kernel compiler, not a complete PyTorch graph compiler. LM7 should
reuse TorchInductor rather than attempting to lower PyTorch graphs directly to
Triton.
